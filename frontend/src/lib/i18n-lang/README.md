# Переводы: где они лежат и как их править

Один язык — один файл: `ru.ts`, `en.ts`, `kk.ts` и остальные восемь.
**Это и есть словарь**, а не копия чего-то. Правьте прямо здесь.

## Добавить или изменить строку

1. Ключ добавляется **в `en.ts` обязательно** — английский рисуется первым и
   служит запасным вариантом для любого языка, где ключа нет.
2. Затем в `ru.ts` и `kk.ts` — это три языка, на которых интерфейс существует
   целиком.
3. Обновите `LANG_KEY_COUNT` в `../i18n-data.ts`, если число ключей изменилось:
   из него переключатель считает покрытие языка. Тест `i18n-split.test.ts`
   упадёт и назовёт язык, если забыть.

Ключи внутри файла отсортированы — держите порядок, тогда в диффе видно правку,
а не перестановку.

## Чего делать нельзя

- **Не возвращайте словарь в `i18n-data.ts`.** Его импортирует клиентский
  провайдер, то есть каждая страница платформы. До 10.08.2026 все одиннадцать
  языков ехали на каждую страницу — 1.3 МБ из 2.5 МБ, которые страница обязана
  загрузить, прежде чем ответить на нажатие. Тест это запрещает.
- **Не импортируйте `../i18n-all` из клиентского кода.** Это агрегат всех
  языков для сервера и тестов; один такой импорт возвращает те же 1.3 МБ.
- **Не импортируйте статически ничего, кроме `en`.** Остальные языки грузятся
  через `loadDict()` из `../i18n.tsx`.

Обе ошибки собираются молча: сборка зелёная, страница работает, просто снова
тяжёлая. Их ловят `__tests__/i18n-split.test.ts` и `e2e/page-weight.spec.ts`.

## Как это устроено

- клиент компилирует только `en` — первый рендер обязан совпасть с серверным,
  а сервер рисует ещё не зная языка посетителя;
- язык посетителя приезжает отдельным куском, запрос стартует до монтирования
  React;
- сервер (`../i18n-server.ts`) знает все языки сразу и рисует нужный по куке.

Замерить вес страницы: `node scripts/page-weight.mjs http://127.0.0.1:3000 /`.
